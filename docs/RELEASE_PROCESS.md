# Publicación de los plugins Digitalisimo

La copia local de Element Pack Pro vive en `reference/bdthemes-element-pack/`, fuera de las carpetas de plugins: es una referencia de investigación, está ignorada por Git y no forma parte de ningún ZIP. `scripts/build-packages.sh` comprueba además que el ZIP de DIGITALÍSIMO Elements no contenga ni mencione Element Pack (ni sus prefijos `bdt-`, `bdt_` o `ep_`): toda la compatibilidad heredada se distribuye en DIGITALÍSIMO Migración (`digitalisimo-migration`), que se instala sólo mientras dura la migración.

Los siete plugins se actualizan de forma independiente desde WordPress. Cada entrega de código debe incrementar la versión en el encabezado PHP y en `tests/validate-suite.mjs` **sólo de los módulos modificados**. Cada versión nueva debe superar la ya publicada para ese módulo.

Los actualizadores sólo pueden cambiar su propia entrada dentro del transitorio `update_plugins`. Si WordPress devuelve `false` o un objeto sin `checked`, deben devolverlo intacto para que WordPress complete el inventario. Una comprobación manual o programada no debe eliminar el transitorio global: debe actualizar únicamente el aviso propio sobre una copia válida y conservar `response`, `no_update`, `checked` y `translations` de terceros.

Desde la lista Plugins, «actualízalo ahora» de un módulo Digitalísimo debe usar `wp.updates.updatePlugin()` para mostrar avance, éxito o error en su misma fila sin salir de la pantalla. El controlador se carga sólo en `plugins.php`, se registra una vez aunque haya varios módulos activos y cada módulo declara su propio archivo mediante `wp_add_inline_script()` antes de cargarlo; no mantener listas fijas de módulos en JavaScript. Los plugins de otros desarrolladores quedan bajo el comportamiento nativo de WordPress. Si la API AJAX de WordPress no está disponible, el enlace conserva su ruta nativa. La validación de paquetes comprueba que los seis ZIP contienen el mismo controlador y prohíbe borrar explícitamente el transitorio global `update_plugins`.

Al enviar a `main` un cambio dentro de cualquiera de los siete directorios de plugins, `.github/workflows/release.yml` ejecuta la validación PHP y la suite completa, detecta qué módulos cambiaron, y comprueba que la versión de cada plugin modificado supera la ya publicada. Si todo pasa, crea una Release con etiqueta numerada `vAAAA.MM.DD.N`, cuyo número `N` es el de la ejecución del workflow. La Release contiene **el ZIP vigente de los siete plugins**: los modificados con su versión nueva y los demás con la misma versión que ya tenían, que no cambia. Sus notas indican qué plugins tienen versión nueva. El workflow falla si falta o sobra un ZIP, o si una versión modificada no avanzó.

También puede iniciarse manualmente desde GitHub Actions. Con slugs separados por espacios, comprueba que esos plugins tienen versión nueva. Con la lista vacía, vuelve a publicar el ZIP vigente de los siete sin cambiar ninguna versión, por ejemplo si en la última Release faltara alguno.

Antes de dar la entrega por terminada, revisar que el workflow **Publicar módulos Digitalisimo** terminó correctamente y comprobar que la Release pública tiene los siete ZIPs, con versión nueva en los modificados. Hace falta porque los actualizadores de WordPress y los catálogos de plugins de SEO y Tools sólo leen las 50 Releases más recientes: un plugin que no apareciera en ellas dejaría de encontrarse, para actualizarlo o para instalarlo. WordPress detecta una actualización sólo cuando la versión publicada supera la instalada; la detección también depende de la próxima consulta de actualizaciones de WordPress. El primer paso de instalaciones con actualizadores antiguos puede requerir actualizar el ZIP una vez para incorporar el mecanismo `Update URI` nativo.

SEO 1.0.165 agrega una comprobación independiente cada cinco minutos con WP-Cron y actualiza el aviso de `update_plugins` sin esperar la caché horaria compartida. WP-Cron depende del tráfico o de un cron del servidor; una instalación todavía anterior a 1.0.165 conserva el comportamiento de su actualizador previo hasta instalar esa versión.

DIGITALÍSIMO Elements incluye el núcleo de Elementor en `digitalisimo-elements/elementor/`. Cuando Elementor publica una versión (en especial si corrige seguridad) se trae con `bash scripts/sync-elementor-core.sh X.Y.Z`, se valida con `bash tests/playground/core-switch.sh` y `CORE=bundled bash tests/playground/interaction.sh` y se publica como una versión más de Elements. El procedimiento completo está en [ELEMENTOR_CORE.md](ELEMENTOR_CORE.md).

Para validar localmente la suite completa: `bash scripts/build-packages.sh /tmp/digitalisimo-suite` y `DIGITALISIMO_PACKAGE_DIR=/tmp/digitalisimo-suite node tests/validate-suite.mjs`. Para validar una publicación individual: `bash scripts/build-packages.sh /tmp/digitalisimo-release digitalisimo-tools` y `DIGITALISIMO_PACKAGE_DIR=/tmp/digitalisimo-release node scripts/verify-release.mjs --remote digitalisimo-tools`. Usar directorios vacíos para que los ZIPs históricos no se mezclen con una entrega nueva; conservar los anteriores en `rollback/`.
