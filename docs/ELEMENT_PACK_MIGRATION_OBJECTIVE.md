# Objetivo de continuidad: Element Pack Pro → DIGITALÍSIMO Elements

Este documento es el punto de entrada para cualquier agente que continúe la migración. El objetivo es incorporar **los widgets útiles de Element Pack Pro** a `digitalisimo-elements` como componentes propios, funcionalmente completos y optimizados desde su arquitectura, sin romper Elementor, las páginas existentes ni el Slider Optimizado. DIGITALÍSIMO SEO puede optimizar después la salida pública, pero un widget de Elements debe ser correcto, accesible y eficiente por sí mismo.

La petición del usuario es terminar primero el bloque prioritario de [63 componentes](element-pack-priority.md) (53 widgets y 10 extensiones), y después continuar con los restantes del [inventario de 263 IDs Elementor](element-pack-inventory.md). El orden interno puede agrupar componentes que comparten motor, pero no sustituir esta prioridad por una puntuación técnica. El trabajo **no está terminado**: existen bases propias de algunos widgets, pero la equivalencia completa, la migración de documentos legacy y la validación real en WordPress siguen pendientes.

## Fuente, alcance y procedencia

- La copia `digitalisimo-elements/bdthemes-element-pack/` es **sólo referencia local de análisis**. No se instala, no se ejecuta, no se importa en runtime y está excluida del ZIP. El repositorio no distribuye sus pantallas de activación/desactivación, administración, licenciamiento ni servicios remotos. Se incorporan widgets; las 10 extensiones prioritarias se evalúan por separado y sólo si pueden integrarse sin efectos globales imprevistos.
- La referencia declara GPLv3, pero **cada recurso reutilizado** (código, biblioteca, icono, imagen, fuente o plantilla) exige revisión de procedencia y licencia. Conservar avisos de copyright, fuente y cambios cuando corresponda; registrar cada incorporación en [third-party-licenses.md](third-party-licenses.md) y en `digitalisimo-elements/DIGITALISIMO_CHANGES.md`. No inferir que todos los assets del paquete tienen la misma licencia.
- DIGITALÍSIMO Elements ya es un derivado de PRO Elements para Elementor gratuito. Mantener compatibilidad con ese motor y sus documentos; no copiar motores paralelos de formularios, WooCommerce, Theme Builder o Loop si el derivado ya los resuelve. No presentar el trabajo como producto oficial de Elementor ni como garantía de acceso a servicios de pago.

## Estado comprobable antes de trabajar

La fuente de verdad es el código y las pruebas, no una etiqueta de «migrado» en un documento. Al escribir esta guía, `modules/digitalisimo-widgets/class-registry.php` registra **38 widgets propios**: Video Player, User Register, Total Count, Tags Cloud, Table, QR Code, Product Grid, Notification, Icon Nav, Icon Mobile Menu, Google Reviews, Featured Box, Fancy Tabs, Fancy Slider, Fancy Icons, Device Slider, Fancy Card, Custom Gallery, Creative Button, Comparison List, Content Switcher, Dual Button, Call Out, Breadcrumbs, Animated Heading, Advanced Icon Box, Advanced Divider, Advanced Button, Accordion, Animated Link, Fancy List, Document Viewer, Brand Carousel, Logo Carousel, Advanced Heading, Brand Grid, Logo Grid y Scroll Button. El Slider Optimizado vive aparte en `modules/digitalisimo-slider/`, conserva el ID `digitalisimo-slider-optimizado` y **no equivale automáticamente** a `bdt-slider`. Sólo Animated Link ofrece un adaptador de lectura `bdt-animated-link`, condicionado a que Element Pack no esté activo y el ID no esté ocupado.

Estas bases no significan paridad completa. El [mapa de migración](migration-map.json) registra controles, destinos y pendientes por ID; la [prioridad](element-pack-priority.md) indica qué componentes van primero; el [plan técnico](element-pack-migration-plan.md) explica los pilotos; el [grafo de dependencias](element-pack-dependency-graph.md) y su JSON permiten identificar motores y recursos compartidos. Regenerar el inventario con `python3 scripts/inventory-element-pack.py` sólo cuando cambie la referencia o el método de análisis, y revisar el diff antes de aceptarlo.

La extensión prioritaria **Duplicator** tiene una base propia en `digitalisimo-duplicator.php`: aparece en las filas de entradas, páginas, CPT públicos y plantillas Elementor del sitio actual, crea un borrador y conserva datos editoriales y de Elementor. Excluye productos, medios y tipos transaccionales; omite bloqueos y cachés. No depende del loader de Element Pack. Su validación automática no sustituye una prueba real con WordPress Multisite y plugins de metadatos.

## Arquitectura obligatoria

1. Registrar cada widget nuevo con ID `digitalisimo-*` en el registro propio. Separar modelo de datos, salida y dependencias. Declarar handles concretos; registrar los recursos de forma reutilizable y cargarlos sólo cuando Elementor use el widget. No cargar UIkit, Swiper, CSS o JS de Element Pack de forma global. Un motor compartido debe atender widgets con la misma necesidad sin acoplar sus controles.
2. Preservar configuraciones existentes de Elementor. No ocupar un ID `bdt-*` por semejanza de nombre. Un adaptador legacy sólo se añade tras demostrar equivalencia de controles, repeaters, skins, estados responsivos, comportamiento y salida. Si Element Pack está activo o registró el ID, no competir por él.
3. No reescribir `_elementor_data` implícitamente. Una conversión permanente necesita mapa explícito, previsualización, respaldo, operación por sitio, reversión y pruebas de documentos reales. Un mapa incompleto mantiene el estado pendiente.
4. Funcionar con Elementor gratuito y el derivado actual en WordPress normal, en un sitio de Multisite y con activación de red. Resolver datos y URLs dentro del sitio en curso. No depender de SEO, Tools ni de otro módulo DIGITALÍSIMO para que el widget funcione.
5. Producir HTML semántico, ALT y nombres accesibles cuando procedan, foco visible, teclado funcional, sanitización y escape. Respetar `prefers-reduced-motion`; evitar contenido invisible para SEO y schema duplicado. Tratar vacíos, enlaces inválidos, fallos de terceros y ausencia de plugins opcionales sin errores fatales.
6. Conservar el Slider Optimizado como componente independiente y estable. Antes de tocar motores de carrusel, probar varias instancias en la misma página, dirección, espejo, bucle, carga inicial y tamaños escritorio/tableta/móvil. Sus regresiones previas se documentan en `digitalisimo-elements/SLIDER_OPTIMIZADO.md` y `docs/measurements/2026-10-07-slider-mirror-loop.md`.

## Cómo completar un widget

Tomar el siguiente componente de [la lista prioritaria](element-pack-priority.md). Inspeccionar en la referencia sus controles, dependencias, markup, estados y casos especiales; comprobar si PRO Elements ya ofrece una función equivalente. Registrar en `migration-map.json` la decisión (`RECONSTRUIR`, `COMPARTIR`, `ADAPTAR`, `MIGRAR` o `DESCARTAR`) y la justificación. Implementar primero un widget `digitalisimo-*` con assets condicionales; no registrar el alias `bdt-*` durante esta fase.

Antes de marcarlo completo, comprobar en editor y frontend: controles y variantes responsivas, contenido real y vacío, errores, accesibilidad, activación por sitio/red y WordPress individual, coexistencia con Element Pack, y comparación visual en escritorio/tableta/móvil. Medir de forma comparable nodos DOM, solicitudes y KB de CSS/JS cargados, tiempo de render y CLS. Documentar diferencias deliberadas y funcionalidades aún ausentes. Sólo entonces evaluar el adaptador legacy y la conversión de documentos. Una prueba unitaria que replica el HTML esperado no reemplaza estas comprobaciones.

Para cada lote, actualizar [PLUGIN_ROADMAP.md](PLUGIN_ROADMAP.md), `migration-map.json`, la prioridad cuando cambie un estado, las pruebas y la atribución. Ejecutar las pruebas específicas `tests/elements-*.php`/`.mjs` pertinentes y la suite de paquetes. Si se modifica el plugin, incrementar **sólo** la versión de Elements, preparar su ZIP, comprobar `unzip -t`, publicar por `main` y verificar que el workflow y la Release contienen únicamente su asset, según [RELEASE_PROCESS.md](RELEASE_PROCESS.md). Los cambios exclusivos de documentación no requieren versión ni ZIP.

En 4.3.0.81 Visibility Controls deja de ser una cobertura parcial: `modules/digitalisimo-conditions/` registra 28 condiciones en el gestor nativo de Display Conditions mediante `elementor/display_conditions/register` (16 sólo cuando WooCommerce está activo). Las reglas de fecha y hora de la referencia se cubren con las nativas combinadas en un grupo Y; ACF, con la condición nativa de etiquetas dinámicas. Sigue pendiente una conversión opcional al formato nativo de Display Conditions.
